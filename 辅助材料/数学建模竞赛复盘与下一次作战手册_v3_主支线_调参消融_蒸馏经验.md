# 数学建模竞赛复盘与下一次作战手册

> 基于五一数学建模竞赛与华数杯 VLSI 布图规划两次实战复盘。  
> 核心目标不是“做更多”，而是：**选对问题、先定数学主线、让工程围绕证据服务、把最强结果讲清楚。**

---

## 一、总原则：做少、做深、证据先行

这两次比赛最核心的经验可以压缩成一句话：

> **先数学模型，后工程实现；先确定主线和评价协议，再写代码；工程实现必须从一开始就服务于最终论文里的结果、消融、图片和可复现性。**

再进一步：

- 不要把“我做了很多”误认为“论文很强”。
- 不要因为某个分支已经投入很多时间，就强行把它留在正文里。
- 不要让评委替你推断你已经做过什么。
- 不要把严谨理解成“把所有结论说小声一点”。
- 不要把 fancy method 当成 attractive narrative 的唯一来源。
- 真正好的论文，是**问题结构—模型选择—实验验证—结果解释**形成闭环。

对于算法优化题，还应再加一条：

> **不要只交一个“算法”，要尽量交一个“可验证的求解系统”：representation + solver + verifier + certificate / bound + provenance。**

也就是说，最终说服评委的不是“我们用了 SA / GA / MILP / MCTS”，而是：

- 解为什么可行；
- objective 到底是多少；
- 有没有独立 verifier；
- 有没有 lower bound / exact small-case / benchmark 可以校验；
- heuristic 找不到解时，是否避免把 non-hit 误写成 infeasible；
- 最终 headline result 是否能追溯到具体 seed、budget、参数与 postprocess。

---

# 二、五一竞赛：第一次完整闭环，但 research taste 还不成熟

五一那次最大的价值，不是“二等奖”，而是第一次完整经历了：

**模型设计 → 工程实现 → 实验 → 图片 → 论文 → 评审反馈**

它暴露出来的主要问题，不是“不会做”，而是**做得太多、主线不够克制、证据预算不足**。

## 2.1 不要做 Model Zoo

当时用了很多方法：

- OLS
- GBDT
- XGBoost
- DNN 残差补偿
- Ridge
- PatchTST
- SHAP
- Savitzky-Golay
- 反速度模型
- 单调回归
- Softplus 物理约束
- 各类特征工程与异常检测

单独看都合理，但放在一起容易让论文变成：

> “我不知道哪个最好，所以全跑一遍。”

真正成熟的做法应该是：

1. 先根据问题结构确定 **major model**；
2. 其他模型作为 baseline / validation；
3. 不成功的模型只保留必要的 negative result；
4. 不要让所有模型在正文里“人人平等”。

### 核心教训

> **模型数量不是创新度。选择质量比数量更重要。**

---

## 2.2 主模型要先由问题结构决定，再由实验验证

五一有些部分的逻辑容易变成：

> 先把模型跑完 → 发现 XGBoost 赢了 → 再解释为什么 XGBoost 适合这个数据。

以后应改成：

\[
\text{Problem Structure}
\rightarrow
\text{Model Hypothesis}
\rightarrow
\text{Baseline / Evaluation}
\rightarrow
\text{Confirm or Reject}
\]

而不是：

\[
\text{Model Zoo}
\rightarrow
\arg\min(\text{RMSE})
\rightarrow
\text{给冠军补故事}
\]

### 核心教训

> **叙事要是“验证原判断”，而不是“根据结果反推理由”。**

---

## 2.3 漂亮指标必须先问：它到底测了什么？

五一里一步位移预测 \(R^2\) 极高，但一步位移本身强烈继承上一时刻观测值，因此这个指标天然容易漂亮。

真正困难的目标往往是：

- 速度预测
- 增量预测
- 极值/突变预测
- 外推稳定性

所以以后不能只看哪个数字最漂亮，而要问：

> **这个指标真的反映了模型能力，还是数据结构本身让它容易变高？**

### 核心教训

> **Primary metric 要能真正反映 task difficulty。**

---

## 2.4 指标冲突必须提前定义裁决规则

例如复杂模型可能：

- RMSE 更好
- \(R^2\) 更好
- 但 MAE 更差

如果结果出来后再解释“为什么 RMSE 更重要”，容易显得 post-hoc。

以后应该在模型运行前先定：

- Primary metric
- Secondary metric
- 如果指标冲突，以什么原则裁决
- 是否需要对突变段和普通段分开报告

### 核心教训

> **评价协议必须早于最终结果。**

---

## 2.5 物理机制不能只停留在 feature engineering

“降雨 → 孔压 → 有效应力 → 深部剪切 → 表面位移”这种链条，如果最后只是变成：

- 降雨累计量
- 孔压差分
- 微震累计
- 滞后项
- 滚动项

然后全部塞进 XGBoost，那么它更准确地叫：

> **physics-informed feature engineering**

而不是强意义上的 physics-driven model。

更深的物理嵌入应该真正改变模型可行空间，例如：

- 参数符号约束
- 单调性约束
- 阶段门控
- 守恒关系
- 力学关系
- 物理损失项
- 结构化状态转移

### 核心教训

> **如果论文说“物理驱动”，最好让物理规律进入模型结构，而不是只负责解释输入变量。**

---

## 2.6 严谨不是写 caveat，而是量化 uncertainty

五一里已经知道某些外推结果不应被当作精确时刻，但只写“仅作趋势参考”仍然不够。

更好的做法是：

- bootstrap confidence interval
- 参数扰动
- sensitivity analysis
- prediction interval
- error band

### 核心教训

> **严谨不是把声音调小，而是给不确定性装刻度。**

---

## 2.7 最大的现实问题：时间预算被模型本身吃光了

五一真正的问题不是“不知道要做 uncertainty / validation”，而是：

> **主线模型跑完以后，已经没有时间做完整验证。**

这说明比赛里必须从一开始分配：

\[
T_{\text{total}}
=
T_{\text{model}}
+
T_{\text{implementation}}
+
T_{\text{debug}}
+
T_{\text{ablation}}
+
T_{\text{validation}}
+
T_{\text{figures}}
+
T_{\text{writing}}
\]

而不是只预算前三项。

### 核心教训

> **不是“下次在十几个模型后面再加 bootstrap”，而是“少做几个模型，把时间留给主模型验证”。**

---

# 三、华数杯：技术主线更硬，但出现了“过度校正”

华数杯相较五一，最大的进步是：

- 主线更清楚
- solver 工程更完整
- verifier 更严格
- 结果更硬
- 证据意识更强
- 对“可行上界 / 全局最优 / non-hit”区分更严谨

最终一等奖也证明：

> **技术主线已经具备很强竞争力。**

但也出现了几个新问题。

同时，这次比赛也确认了一件此前没有总结得足够明确的事：

> **优化题的竞争力，往往不来自“元启发式算法名字更高级”，而来自表示、邻域、约束处理、精炼、验证与上下界这些 problem-specific 结构。**

B*-Tree + contour + Fast-SA + LP refinement 的价值，并不只是“用了模拟退火”，而是不同组件各自承担了明确角色：

- B*-Tree：编码离散拓扑结构；
- contour：快速维护合法布局；
- Fast-SA：在巨大组合空间中搜索；
- LP refinement：固定离散关系后继续压缩连续自由度；
- verifier：独立检查几何/约束/目标；
- lower bound / exact search：在可行时给出更强的最优性证据。

这类结构化 solver，比“裸 GA / 裸 PSO / 裸 SA”更值得投入。

---

## 3.1 从 overclaim 走到了 underclaim

五一有些地方：

\[
\text{Narrative Confidence} > \text{Evidence Strength}
\]

华数杯则有些地方变成：

\[
\text{Narrative Confidence} < \text{Evidence Strength}
\]

典型表现：

- “可行上界”重复出现
- “不构成严格排名”
- “不归因于扩展组件”
- “限时未发现不等于不可行”

这些边界本身是对的，但不需要反复强调。

### 核心原则

\[
\boxed{
\text{Claim Strength}
\approx
\text{Evidence Strength}
}
\]

- 事实：大胆说
- 经验证结果：大胆说
- 因果归因：谨慎
- 泛化结论：谨慎
- 全局最优：只有证明后才说
- 跨平台效率：没有公平预算不要说

### 核心教训

> **证据边界说一次，边界以内使劲 claim。**

---

## 3.2 Fancy 不等于 attractive

这次为了让论文“不 plain”，加入了：

- AOS
- 多链共进化
- 连续坐标搜索
- Per-RMAP
- CP-SAT repair
- 其他 experimental branch

但很多扩展没有稳定的 matched-budget evidence。

于是它们反而制造了新的 reviewer questions：

- 为什么需要？
- 真的有提升吗？
- 最终结果到底是不是靠它？
- 既然没证明，为什么正文写这么多？

### 核心教训

> **真正 attractive 的 narrative 来自“问题张力”，不是算法名数量。**

比如华数杯真正自然的故事其实已经很强：

1. 离散拓扑负责大尺度搜索；
2. 固定拓扑后仍有连续自由度，所以用 LP 精炼；
3. heuristic non-hit 不能证明 infeasible，所以 Q3 要区分 witness、lower bound 与搜索记录；
4. Q4 规模小，可以切 exact backtracking 并闭合下界。

这已经足够形成主线。

---

## 3.3 沉没成本不参与正文保留决策

这是这次最深的教训之一。

心理误区：

> “这个模块我都写了、都跑了，不写进论文不亏了吗？”

正确问题应该是：

\[
\text{Keep if }
\mathbb E[
\Delta \text{Paper Quality}
\mid
\text{from now on}
]
>0
\]

而不是：

\[
\text{Keep because I already spent 8 hours on it}
\]

### 论文里的三层结构

#### Hero
真正产生 headline result、证据完整、没有它故事就不成立。

#### Supporting Cast
没有进入最终主线，但回答了一个重要问题，例如：

> “为什么不用 Sequence Pair / DNN / AOS？”

#### Graveyard
做过、调过、失败过，但不值得进入正文。

### 核心教训

> **Code repository 可以是坟场，Paper 不是墓志铭。**

---

## 3.4 失败实验可以保留，但必须降级

例如 AOS 在短预算配对消融中未呈现正收益。

这类结果并不是“不能写”，而是应该换一种身份：

> “我们检验了该增强组件，但在当前预算下未见稳定收益，因此正式结果不依赖它。”

一句话或一张小表足够。

### 核心教训

> **Negative result 的价值在于淘汰复杂度，而不是让失败模块占正文豪华套房。**

---

## 3.5 重要信息不能要求评委自己 infer

华数杯里很多东西其实都存在：

- 统一 solver
- mode 切换
- 参数默认值
- CLI arguments
- README
- seed
- budget
- verifier
- provenance

问题是它们有些藏在：

- 代码
- README
- 附录
- 隐含表述

读者必须自己拼起来。

以后凡是会影响评委判断的内容，都应该显式写：

- 最终采用什么配置
- 参数什么时候冻结
- 哪些参数共享
- 哪些因问题变化
- budget 如何分配
- 是否针对单 case 事后调参
- seed
- postprocess
- verifier

### 核心教训

> **把隐含信息显式化，把显式信息压缩化。**

---

## 3.6 正文、README、代码要分层承担责任

### PDF 正文
负责让评委在 30 秒内知道：

- 模型是什么
- 为什么这样设计
- 参数不是拍脑袋
- 结果从哪里来
- 是否验证
- 哪些结论能成立

### README
负责：

- 一键复现流程
- CLI arguments
- 配置说明
- 输入输出
- 文件结构

### 代码
负责：

- executable truth
- 参数默认值
- solver implementation
- verifier
- experiment scripts

### 核心教训

> **附件负责证明“可以复现”；正文负责让人不用复现也相信“确实可复现”。**

---


## 3.7 Verifier / Certificate 比“算法名”更值钱

优化题里，最容易被低估的是**结果证据**。

“我们的算法取得了较优解”只是叙述；更硬的表达应该是：

\[
\boxed{
\text{Solution Witness}
+
\text{Independent Verifier}
+
\text{Lower Bound / Exact Check}
+
\text{Gap}
}
\]

如果条件允许，应尽量构造以下至少一种证据：

- 小规模实例的 exact optimum；
- LP / MILP / relaxation lower bound；
- 可行解 witness；
- 独立 constraint checker；
- objective 独立重算；
- 与公开 benchmark / baseline 的同定义比较；
- optimality gap。

### 特别注意

\[
\text{Heuristic Non-hit} \neq \text{Infeasible}
\]

“在给定预算内没有找到可行解”只能说明搜索过程 non-hit，不能推出“问题无解”。

### 核心教训

> **优化题不要只交一个答案，要尽可能交一份证明答案可信的证据链。**

---

## 3.8 统一 Solver 比“四问四套模型”更有价值

如果多问之间共享基本结构，应尽量复用：

- representation
- neighborhood
- feasibility logic
- evaluator
- verifier
- logging
- experiment harness

每一问只改变：

- objective
- constraint set
- mode
- small amount of problem-specific logic

理想结构是：

\[
\boxed{
\text{Unified Solver Backbone}
+
\text{Question-specific Objective / Constraints}
}
\]

这样做的好处不只是代码少：

- 更容易验证；
- 更容易复现；
- 参数更容易统一解释；
- 论文叙事更连贯；
- 修改一处 bug 不需要同步四套实现；
- 可以把更多时间留给消融与结果分析。

### 核心教训

> **比赛不是比谁造四个模型，而是谁用最少的结构解释最多的问题。**

---

## 3.9 精确方法与启发式不是二选一

优化题里不要形成错误二分：

> “规模大，所以只能 heuristic。”

更成熟的做法是混合：

\[
\text{Exact / Relaxation}
\leftrightarrow
\text{Heuristic Search}
\]

常见组合：

- 小规模 exact，大规模 heuristic；
- MILP / CP-SAT 给 lower bound 或 repair；
- heuristic 提供 warm start；
- 固定离散拓扑后交给 LP 做连续精炼；
- exact solver 校验部分 case；
- relaxation 用于判断当前解还有多少改进空间。

### 核心教训

> **Exact 方法负责“证明”，heuristic 负责“找”；能合作就不要让它们互相抢饭碗。**

---

## 3.10 工程能力必须翻译成论文里的“可见证据”

这次比赛暴露出的一个典型问题是：

> **工程实现其实很强，但论文没有把工程价值全部显式翻译出来。**

例如代码里可能已经有：

- 统一 solver；
- mode 切换；
- verifier；
- 多 seed；
- runtime logging；
- 参数配置；
- LP refinement；
- repair；
- fallback；
- exact small-case；
- provenance。

但如果正文只写：

> “采用模拟退火算法求解。”

那这些工程价值几乎全部被压扁了。

以后必须把关键工程设计转译成论文语言：

> “为什么需要这个模块 → 它解决什么数学困难 → 如何验证它确实发挥作用。”

工程里的每个关键模块最好都能对应到论文中的以下至少一个元素：

- 一个数学动机；
- 一个消融实验；
- 一张图；
- 一个 verifier；
- 一个复杂度说明；
- 一个稳定性/鲁棒性结果；
- 一个更强的 claim。

### 核心教训

> **代码里藏着的能力，评委不会自动执行 `git clone` 后替你发现。**

---

# 四、工程实现与实验纪律：必须从“论文需要什么证据”反推代码

这是以后最重要的比赛节奏要求之一。

## 4.1 先数学模型，后工程实现

不要一拿题就直接 coding。

第一阶段先完成：

1. 问题结构分析
2. 数学变量
3. 目标函数
4. 约束条件
5. 主模型假设
6. Primary metric
7. Baseline
8. 需要验证什么
9. 最终论文要展示哪些图、表、指标

只有这些基本冻结后，才开始大规模工程实现。

对于算法优化题，建议在这一阶段额外明确：

- representation / state 如何编码；
- feasibility 是“始终保持”还是“搜索后 repair”；
- neighborhood 是否具有 problem-specific 含义；
- objective 能否增量计算；
- 是否存在可用于验证的小规模 exact solver；
- 是否能推 lower bound / relaxation；
- 是否需要后处理 refinement；
- 最终 verifier 是否与 solver 解耦。

这一步决定的往往不是“代码风格”，而是 solver 的上限。

### 原因

如果先写代码，后想论文，很容易出现：

- 日志没存
- baseline 没跑
- seed 没记
- 中间状态没留
- 关键图无法重画
- 消融只能重跑
- 参数不知道哪个版本对应最终结果

---

## 4.2 消融实验必须前置设计，而不是最后补

以后如果某个模块是**可调参数 / 可选组件 / 算法增强项**，就必须在工程设计阶段问：

> **这个东西最后怎么证明有用？**

如果不能回答，就不要轻易让它进入主线。

### 所有可调参数应尽早分类

#### A. 必须冻结的核心参数
例如：

- 初始温度策略
- cooling schedule
- moves per temperature
- penalty weight
- population size
- search budget

#### B. 可以调，但必须做消融/敏感性分析的参数
例如：

- AOS 权重
- penalty coefficient
- LP refinement 权重
- threshold
- neighborhood probability

#### C. 纯工程参数
例如：

- worker 数
- logging frequency
- file path
- visualization DPI

### 原则

> **凡是你计划在论文里声称“这个参数/模块有作用”，就必须提前安排 ablation。**

不要到了最后才发现：

> “这个参数我调了半天，但没有公平对照。”

---

## 4.3 有调参空间的组件，要尽早完成调参 + 消融

以后不能再出现：

> “主模型跑完了，最后再看看参数敏感性。”

正确节奏：

1. 小规模 pilot run
2. 冻结合理范围
3. 设定 baseline
4. 做小预算快速消融
5. 确定正式配置
6. 再跑大规模正式实验

### 理想流程

\[
\text{Pilot}
\rightarrow
\text{Parameter Screening}
\rightarrow
\text{Ablation}
\rightarrow
\text{Freeze}
\rightarrow
\text{Full Run}
\]

而不是：

\[
\text{Full Run}
\rightarrow
\text{发现结果不错}
\rightarrow
\text{临时补解释}
\]

---

## 4.4 图片必须在工程实现阶段就规划

比赛论文不是“代码跑完以后再想画什么图”。

在写 solver / model 时就应该明确：

- 需要什么布局图
- 需要什么收敛曲线
- 需要什么消融柱状图
- 需要什么 sensitivity curve
- 需要什么 uncertainty band
- 需要什么 baseline comparison
- 需要什么 residual / error plot
- 需要什么流程图
- 需要什么阶段识别图

### 工程上必须提前保存

- 每轮 objective
- best-so-far
- runtime
- seed
- 参数
- 中间状态
- 最终坐标
- baseline 结果
- ablation 结果
- verifier 结果
- prediction interval / bootstrap samples（如需要）

### 核心教训

> **图片不是论文阶段的装饰，是实验设计的一部分。**

以后正式结果至少记录：

\boxed{
\text{Result}
+
\text{Variant}
+

+
\text{Budget}
+
\text{Parameters}
+
\text{Postprocess}
+

```text

figure_data.csv

```

这样写论文时不需要“凭记忆考古”。

## 4.6 模型选择采用“稳定主线 + 实验支线”双轨制

比赛中的模型不必刻意追求“最新”。一个经典方法只要与问题结构高度匹配、结果稳定、证据完整，就完全可以承担主模型；反过来，新方法如果只是因为“新”而引入，却缺乏稳定性、公平对照或解释价值，并不会自动变成亮点。

模型选择的优先级应理解为：

\[
\boxed{
\text{Problem Fit}
+
\text{Result Quality}
+
\text{Evidence Strength}
+
\text{Narrative Value}
>
\text{Novelty Alone}
}
\]

但在效果接近、实现成本可控时，应主动向更新、更强、更贴合问题结构的方法靠拢。

以后默认维护两条线：

### Mainline：负责稳定拿分

主线必须满足：

- 数学逻辑扎实；
- baseline 完整；
- 参数与评价协议清晰；
- 多次运行稳定；
- 结果足够漂亮；
- 有关键消融、敏感性或验证证据；
- 能在比赛结束前稳定交付。

主线的职责不是炫技，而是把整篇论文的下限抬高。

### Experimental Branch：负责探索上限

主线跑通以后，可以单独开 experimental branch，允许明显更激进：

- 最新论文方法；
- hybrid solver；
- LNS / MCTS / neural heuristic；
- learning-assisted optimization；
- adaptive operator / adaptive search；
- 新颖 representation；
- 多阶段求解；
- 其他“看起来很骚，但数学上站得住”的方法。

支线可以大胆，但必须与主线隔离。它不能绑架正式结果，也不能因为投入了很多时间就自动进入正文。

实验性方法想晋级正文，至少应证明以下一个或多个增益：

\[
\Delta \text{Performance} > 0,
\quad
\Delta \text{Robustness} > 0,
\quad
\Delta \text{Efficiency} > 0,
\quad
\Delta \text{Interpretability} > 0
\]

或确实产生新的机制洞见 / narrative value。

### 晋级原则

> **“先进”只获得实验资格，不获得正文编制。**

如果实验支线效果惊艳，则升级为 supporting highlight，证据特别强时再进入 hero narrative；效果一般就进 appendix；失败直接删。

代码仓库可以是赛博动物园，PDF 不行。

## 4.7 所有正式模型必须先写 Implementation Spec

以后任何准备进入主线、baseline 或关键支线实验的模型，在正式 coding 前，都应拥有足够详细的 implementation specification。

不能只写：

> “采用 Transformer 预测。”

或者：

> “采用模拟退火算法求解。”

这类描述对实现几乎没有约束力，也很容易让不同队员 / coding agent 写出不同的东西。

Implementation Spec 至少必须明确以下内容。

### Problem Spec

- 输入与输出；
- decision variables / prediction target；
- objective；
- constraints；
- 数据范围；
- train / validation / test protocol；
- 评价指标与裁决规则。

### Model / Solver Spec

若为 ML / DL：

- 输入 tensor shape；
- preprocessing；
- feature definition；
- normalization；
- architecture；
- hidden dimension / layer 数；
- activation / normalization / dropout；
- output head；
- loss function；
- optimizer / scheduler；
- early stopping。

若为优化算法：

- state / representation；
- initialization；
- neighborhood / operators；
- feasibility mechanism；
- repair；
- objective evaluation；
- incremental evaluation；
- acceptance rule；
- termination；
- local refinement；
- exact / relaxation interface；
- verifier。

### Parameter Spec

- 默认值；
- 搜索范围；
- 参数来源；
- 哪些提前冻结；
- 哪些需要调参；
- 调参协议；
- random seed；
- compute budget。

### Experiment Spec

- baseline；
- primary / secondary metric；
- ablation；
- number of seeds；
- matched budget；
- sensitivity；
- uncertainty；
- failure handling；
- success / kill criterion。

### Logging Spec

- 必须保存哪些 metric；
- 哪些 intermediate state；
- 哪些 trajectory；
- logging frequency；
- provenance；
- figure data。

### Output Spec

- result file；
- metrics；
- verifier；
- checkpoint；
- visualization data；
- final figure requirements。

理想流程不再是：

\[
\text{Idea} \rightarrow \text{Code}
\]

而是：

\[
\boxed{
\text{Idea}
\rightarrow
\text{Implementation Spec}
\rightarrow
\text{Implementation}
\rightarrow
\text{Verification}
}
\]

Implementation Spec 是数学模型与工程实现之间的接口契约。

尤其使用 LLM / coding agent 时，应坚持：

> **不要让 agent 替我们决定模型是什么；让 agent 按冻结后的 specification 实现、测试和产出证据。**

## 4.8 调参、消融、敏感性与冻结必须严格分工

这四件事不能混在一起。

- **Tuning** 回答：这个组件应该怎么设置？
- **Ablation** 回答：这个组件到底该不该存在？
- **Sensitivity** 回答：结论是否过度依赖某一个参数值？
- **Freeze** 回答：什么时候停止继续看结果改配置？

正式流程应当是：

\[
\boxed{
\text{Model Hypothesis}
\rightarrow
\text{Pilot}
\rightarrow
\text{Tune}
\rightarrow
\text{Ablate}
\rightarrow
\text{Sensitivity}
\rightarrow
\text{Freeze}
\rightarrow
\text{Full Evaluation}
\rightarrow
\text{Claim}
}
\]

### 调参：找“稳定好区间”，不是找幸运神仙点

调参阶段目标不是无限寻找理论最优超参数，而是快速找到：

- 稳定区域；
- 性能合理区域；
- 不明显退化的参数范围；
- 计算成本可接受的配置。

优先考虑 coarse-to-fine / random search / TPE / Bayesian optimization / successive halving 等方法，但必须提前规定：

- search space；
- search budget；
- optimization metric；
- validation protocol；
- seed policy；
- early stopping；
- final selection rule。

主线尤其应追求：

\[
\boxed{
\text{Robust Good} > \text{Fragile Best}
}
\]

宁愿选择邻域内都稳定优秀的参数平台，也不要只在一个尖锐参数点上跑出神迹。

### Pilot 只负责筛选，不直接产生 headline result

Pilot 可以少 seed、少 epoch、少 iteration、小规模 instance、低 compute budget。

正式结果必须在 frozen configuration 下重新运行，不能直接从大量 pilot 中挑最好的一次当正式结果。

### 消融：所有准备 claim 的组件都要有证据合同

如果最终方法：

\[
M = A+B+C+D
\]

那么所有准备重点 claim 的模块，都应至少有对应 controlled comparison。

例如要说：

> “LP refinement 改善了最终布局质量。”

则至少需要：

\[
\text{Solver}
\quad vs \quad
\text{Solver + LP Refinement}
\]

并保持其他条件尽量一致。

不要求机械跑满所有 \(2^k\) 组合；只对真正承担 claim 的关键模块做高价值消融。

### 消融必须 matched-budget

公平对照尽量保持：

\[
\boxed{
\text{Same Data}
+
\text{Same Evaluation}
+
\text{Same Compute Budget}
+
\text{Same Seed Set}
}
\]

可按题型匹配：

- wall-clock；
- objective evaluations；
- iterations；
- epochs；
- function calls；
- GPU-hours。

如果算法计算结构不同，应同时报告 quality 与 runtime / compute，而不是只报最终最好值。

### 随机算法不要只报一次

SA / GA / PSO / LNS / MCTS / stochastic DL 等随机方法，正式核心实验应尽可能保存多 seed 分布，并根据成本报告：

- median；
- mean；
- std / IQR；
- best / worst；
- confidence interval（条件允许）。

重点不是机械追求固定 seed 数，而是证明结果不是一个幸运 run。

### 敏感性：检查结论是否依赖单点参数

对于关键连续参数，优先保存参数—性能曲线。

若只有一个参数值表现极好，附近全部崩溃，说明方法脆弱；更理想的是存在宽平台：

\[
f(\theta) \approx \text{stable},
\qquad
\theta \in [\theta_a,\theta_b]
\]

参数较多时，先用 cheap screening / Morris / random search importance 等方法找关键参数，再对关键参数做 OAT / Tornado / Sobol 等有解释价值的分析。不要为了“高级”机械跑全套。

### 正式实验前必须设置 Freeze Point

形成唯一的：

```text
FROZEN_CONFIG.yaml
```

并记录：

- model version；
- parameter values；
- tuning protocol；
- selection metric；
- seed policy；
- compute budget；
- freeze time / commit。

正式结果出来以后，不得在不留版本痕迹的情况下继续偷偷微调。

如必须修改：

```text
v1 -> v2
```

并重新运行受影响实验。

### Evidence Contract

Implementation Spec 中，每个增强模块建议附：

```text
Component:
Claim:
Expected effect:
Controlled variable:
Ablation baseline:
Metric:
Budget:
Seeds:
Success criterion:
Kill criterion:
Required figure:
```

如果一个 fancy component 连“如何证明它有用”都写不出来，大概率就不该进主线。

---

## 4.9 模型采用“双阶段审计”：使用前审模型，使用后审结果

从蒸馏出的高分论文共性看，一个很值得固定成制度的习惯是：

> **检验不能只发生在模型跑完以后。模型使用前先审合法性，模型使用后再审结果可信度。**

### Pre-model Audit：模型使用前

至少检查：

- 目标函数是否真对应题目目标；
- 约束是否漏掉中间过程而只检查终态；
- decision variable 是否真的可控；
- 假设是否与题意、数据和后续模型一致；
- 量纲是否一致；
- 参数单位是否统一；
- 数据分布 / 模型前提是否满足；
- train / validation / test 是否可能泄漏；
- 优化器搜索空间是否覆盖真实可行域；
- 是否存在不可辨识 / 病态 / 数值不稳定问题。

### Post-model Audit：模型使用后

至少检查：

- 结果量级是否符合常识；
- 是否满足所有约束；
- 独立重算 objective 是否一致；
- 收敛轨迹是否正常；
- 不同 seed 是否稳定；
- 与 baseline / 第二方法是否一致；
- 小规模 exact / synthetic ground truth 是否对得上；
- 参数扰动后结论是否稳健；
- 不确定度是否足以改变 headline claim；
- 是否存在“漂亮得离谱”的指标，需要排查泄漏或定义问题。

### 10 维提交审查

最终可以固定成十个问题：

1. 目标一致吗？
2. 约束完整吗？
3. 决策变量定义对吗？
4. 假设合法吗？
5. 数学 / 量纲一致吗？
6. 边界与极限 case 正常吗？
7. 物理 / 业务上合理吗？
8. 数值上稳定、可解吗？
9. 有独立证据验证吗？
10. 能解释为什么得到这个结果吗？

任一关键项答不上来，都不应因为“代码能跑”就直接进入论文定稿。

---

## 4.10 Sanity Check、边界测试与 Ground Truth 必须自动化

很多数模 bug 不是高级 bug，而是：

- 单位错；
- 下标错；
- 时间对齐错；
- 边界漏判；
- 中间约束漏掉；
- objective 算错；
- 结果差 100 倍但没人觉得奇怪。

因此，主模型代码跑通以后，第一件事不是大规模开算，而是建立一组 cheap checks。

### 最低限度的自动检查

- unit / dimension check；
- order-of-magnitude check；
- conservation / sum check；
- min / max / sign check；
- empty / single / full-load boundary case；
- 极端参数极限是否符合理论；
- objective 独立重算；
- feasibility 独立 checker；
- 时间索引 / lead / lag 对齐；
- 随机种子重复运行可复现。

### 优先构造“可知道答案”的小问题

如果可能，应专门构造：

- 手算 toy case；
- brute-force small case；
- exact solver small case；
- synthetic ground truth；
- 退化到已知公式的特殊情形。

这类测试的价值很高，因为它不是问“结果看起来像不像”，而是问：

\[
\boxed{
\text{Known Truth} \stackrel{?}{=} \text{Model Output}
}
\]

尤其优化题，应在冲大实例以前先完成 small-case 对拍。

---

## 4.11 数据题必须单独做 Leakage Audit

“指标漂亮得离谱”不能只当成喜报，也可能是事故现场。

凡涉及 ML / DL / prediction / classification / data-driven model，都必须单独检查：

- 标签是否由某个输入特征直接或间接构造；
- normalization / scaler 是否只在 training data 上 fit；
- feature selection 是否偷看 test；
- imputation 是否使用了未来 / test 统计量；
- 时间序列是否错误 random shuffle；
- lag / rolling feature 是否包含未来信息；
- 同一对象 / 同一事件是否同时落进 train 和 test；
- target encoding 是否跨折泄漏；
- 数据清洗阈值是否由 test 结果反推；
- dirty / clean pipeline 是否把 preprocessing contamination 与 model contamination 混在一起。

尤其时间序列要遵守因果时间：

> **时刻 \(t\) 的特征只能由 \(t\) 及之前真正可获得的信息生成。**

发现 AUC / \(R^2\) / accuracy 异常接近完美时，应优先做 leakage audit，而不是立刻写“模型性能卓越”。

---

## 4.12 每个模型都要提前写 Failure Modes 与 Kill Criteria

在 Implementation Spec 阶段就问：

> **这个方案最可能怎么死？什么现象出现以后应该停止继续烧时间？**

至少列 3 类：

- mathematical failure：假设、约束、可辨识性不成立；
- numerical failure：不收敛、梯度爆炸、搜索空间崩坏；
- empirical failure：matched-budget 下没有稳定增益。

并给触发条件，例如：

```text
Failure mode:
Trigger:
Diagnostic:
Fallback:
Kill criterion:
```

支线尤其必须有 kill criterion。

正确逻辑不是：

> “都写这么多代码了，再调一调吧。”

而是：

\[
\text{Evidence fails}
\Rightarrow
\text{Kill / Downgrade / Fallback}
\]

这能直接对抗沉没成本。

---

## 4.13 Headline Result 尽量拥有第二条独立证据链

对于真正决定论文得分的核心数字，尽量不要让它只依赖一套实现、一种算法或一个指标。

根据题型选择至少一种独立验证：

- exact / brute-force small case；
- 第二种算法；
- relaxation / lower bound；
- independent verifier；
- industrial / physical simulator；
- closed-form special case；
- bootstrap / cross-validation；
- alternative metric；
- public benchmark。

这里不机械要求“每题必须跑三种模型”。

更合理的原则是：

> **每个 headline claim 至少问一次：有没有性质不同的第二条证据能验证它？**

同题多算法横向表的真正价值也不在凑模型数量，而在回答：

- 为什么选当前方法；
- 当前方法的优势来自哪里；
- 换一套方法结论是否仍成立。

---

## 4.14 参数来源也属于证据链

比赛里经常出现某个系数来自：

- 文献；
- 国标 / 行业标准；
- 经验值；
- 题目给定；
- 数据反演；
- 人工设定。

这些来源不能混在一起不解释。

建议每个关键参数都记录：

```text
name
value
unit
source
default/range
estimated_or_fixed
sensitivity_required
```

原则：

- 有工业 / 国家标准时，优先标准；
- 能由当前数据估计时，不轻易只搬文献常数；
- 必须引用外部经验参数时，给合理区间；
- 对结果敏感的外部参数必须做 sensitivity / scenario；
- 文献值不等于真值。

如果参数本身带不确定性，应继续传播到最终输出，而不是只给一个假精确小数。

---

## 4.15 中间轨迹必须视为一级实验产物

以后工程实现默认：

> **任何可能被画成图、用于解释模型行为、用于证明稳定性的信息，都应该保存。**

对于优化算法，至少视情况保存：

- iteration / generation；
- current objective；
- best-so-far；
- feasibility / constraint violation；
- acceptance rate；
- temperature；
- operator / neighborhood；
- incumbent update；
- lower bound / gap；
- runtime；
- population diversity；
- repair count；
- refinement before / after；
- adaptive operator probability / reward。

对于 ML / prediction，至少视情况保存：

- train / validation loss；
- epoch metrics；
- learning rate；
- prediction trajectory；
- residual；
- uncertainty；
- threshold sweep；
- calibration data；
- feature importance / attribution；
- 中间 state / embedding（确实有分析价值时）。

正式实验建议形成：

```text
run_xxx/
├─ config.yaml
├─ metrics.csv
├─ trajectory.csv
├─ events.csv
├─ result.json
├─ verifier.json
├─ figure_data/
│  ├─ convergence.csv
│  ├─ ablation.csv
│  ├─ sensitivity.csv
│  └─ comparison.csv
└─ run.log
```

绘图脚本只读取冻结后的 figure data，避免论文阶段重新解析 stdout 或手工 Excel 炼丹。

最终结果只是一个点，而高质量论文经常真正需要解释的是：

\[
\boxed{
\text{模型是如何走到这个点的}
}
\]

---

## 4.16 从蒸馏材料中“不照搬”的几条规则

这批材料里有一些做法很有启发，但不能机械升级成普适硬约束。例如：

- “所有启发式都必须固定跑 100 个随机解”；
- “所有算法都必须至少 10 个 seed”；
- “同题必须 3 套方法”；
- “仿真误差必须 ≤5%”；
- “Sobol 必须固定 N≥某值”；
- “所有题都必须做某一种高级检验”。

这些数字高度依赖题型、运行成本和数据规模。

真正应该保留的是其背后的原则：

> **随机方法要证明不是幸运 run；核心结果要有独立交叉验证；敏感性采样要足够覆盖参数空间；仿真验证要预先定义可接受误差；实验预算必须与题型和算力匹配。**

以后不要把“高分论文里出现过”误写成“任何比赛都必须这么做”。



# 五、推荐的 72 小时比赛节奏

以下不是死规定，但可以作为默认模板。

## 0–6 小时：问题分析与主线冻结

目标：

- 选题
- 数学建模
- 变量与约束
- 主模型
- baseline
- primary metric
- 必须做的消融
- 必须输出的图片
- 数据接口
- 实验日志格式
- 若为优化题：representation / neighborhood / repair / verifier
- 若可行：小规模 exact / lower bound / relaxation 方案
- headline result 最终需要什么 certificate
- 主线 / experimental branch 如何隔离，支线的 kill criterion 是什么
- 每个正式模型的 Implementation Spec 是否足够直接编码
- 预先列出主要 failure modes / fallback
- Pre-model audit：量纲、边界、数据泄漏、可辨识性是否过关

这一阶段不要沉迷 coding。

---

## 6–24 小时：主模型实现 + 小规模验证

目标：

- 跑通 backbone
- verifier / sanity check
- pilot run
- 参数初筛
- baseline 跑通
- 确认图片数据能保存
- 跑通 sanity checks / boundary tests
- 能构造 toy / exact / synthetic ground truth 的先完成对拍
- 数据题完成第一轮 leakage audit
- 完成参数 screening，并开始形成 frozen config

### 24 小时 checkpoint

必须回答：

- 主线能不能跑？
- baseline 有没有？
- 结果有没有竞争力？
- 哪些参数要冻结？
- 哪些 fancy branch 应该枪毙？
- 小规模实例是否已经与 exact / brute-force 对拍？
- verifier 是否独立于 solver？
- 当前最好结果到底是“可行解”“上界”“下界”还是“已证明最优”？
- 当前 headline result 是否已经有第二条独立证据链？
- 有没有“漂亮得离谱”的指标需要先排查 leakage / metric definition？
- experimental branch 是否达到继续投入的门槛，还是应该 kill / downgrade？

---

## 24–48 小时：正式实验 + 消融 + 图片

这是最重要的 evidence window。

目标：

- 正式多种子
- matched-budget baseline
- 关键消融
- 参数敏感性
- uncertainty（如果题型需要）
- 最终图片
- provenance
- verifier
- matched-budget ablation
- parameter sensitivity / robustness
- multi-seed distribution（随机算法，按成本决定规模）
- uncertainty propagation（参数/数据存在不确定性时）
- experimental branch 只在主线不受影响的前提下冲亮点

### 强制规则

> **超过总赛程约 1/3 后，不再新增需要独立验证的新主方法。**

除非现有主线彻底失败。

---

## 48–60 小时：结果冻结 + 论文主干

目标：

- 最终结果表
- headline figures
- narrative 主线
- 方法描述
- 结果解释
- limitation
- appendix planning

此时不应再大量改 solver。

---

## 60–72 小时：论文、校验与交付

目标：

- 摘要
- 结论
- 图表统一
- 参数表
- configuration matrix
- provenance table
- README
- 附件
- 版本管理
- 最终 verifier
- submission package

---

# 六、论文叙事规则

## 6.1 一篇论文只允许一个主故事

不要让正文变成：

> “我们做了 A、B、C、D、E、F。”

更好的写法是：

> “因为问题存在 X，因此采用 A；A 存在 Y 局限，因此引入 B；最后用 C 验证结果。”

即：

\[
\text{Problem Tension}
\rightarrow
\text{Method}
\rightarrow
\text{Remaining Limitation}
\rightarrow
\text{Next Component}
\]

---

## 6.2 Why 比 What 更重要

“我们用了 B*-Tree + Fast-SA + LP”

只是 what。

更好的叙事：

> “离散拓扑搜索负责改变模块相对结构，但固定拓扑后仍存在连续坐标自由度，因此在保持分离关系的条件下用 LP 继续压缩目标值。”

这才是 why。

对于优化题尤其要避免：

> “我们选择遗传算法，因为遗传算法具有全局搜索能力。”

这种话几乎没有信息量。

更有价值的是解释：

- 为什么这个 representation 能覆盖主要可行域；
- 为什么这个 neighborhood 能有效改变关键结构；
- 为什么某些 move 比随机扰动更合理；
- 为什么需要 repair；
- 为什么需要 LP / local search refine；
- 为什么该 lower bound 有意义。

### 核心原则

> **Problem-specific structure > generic metaheuristic label。**

---



## 6.3 失败分支不参与 headline narrative

如果失败实验不能回答重要问题，就：

- 放 appendix
- 放 repo
- 一句话带过
- 或完全不写

不要因为已经投入时间就强行保留。

---

## 6.4 Caveat 只限制它真正限制的结论

例如：

事实：

> HPWL = 213346.4

可以直接说。

事实：

> 相同 benchmark definition 下低于某公开结果

可以直接说。

不能说：

> 因此算法普遍优于对方。

所以 caveat 应只限制第三句，不要把前两句一起说小声。

---

# 七、团队协作经验

## 7.1 角色不能只按“代码 / 论文”切

建模比赛里：

- 代码决定能画什么图
- 实验决定能写什么 claim
- 论文决定代码必须存什么数据

所以“你写代码、他写论文”经常是假解耦。

---

## 7.2 真正有效的分工是闭环 ownership

一个队友最好能独立负责：

- baseline
- verifier
- 某个子模型
- 数据处理
- 实验自动化
- 某一问完整闭环

并且最终能做到：

> “这一块我不用重新接管。”

如果每个模块最后都要你重新解释、审核、改写，那么协作成本会吞掉收益。

---

# 八、版本与交付管理

最后一个 boss 经常不是数学，而是版本管理。

建议目录：

```text
project/
├─ paper/
├─ code/
├─ results/
├─ figures/
├─ configs/
├─ verifier/
├─ appendix/
└─ README.md
```

正式提交前：

- 只允许一个 release owner
- 建立 `submission-final`
- 锁定 PDF
- 锁定代码
- 锁定结果
- 检查附录编号
- 检查 README
- 检查最终参数
- 检查结果与图表是否一致

最好生成：

```text
MANIFEST.md
```

记录：

- PDF 版本
- commit hash
- 结果文件
- 代码入口
- 参数配置
- 复现命令

---


仍然要在选题阶段判断：

\[
\text{Expected Score}
\approx
\text{可建模性}
\times
\text{可验证性}
\times
\text{可实现性}
\times
\text{论文可讲性}
\]

如果优化题：

- 约束难以形式化；
- 数据/定义缺失；
- 三天内无法得到可信 verifier；
- 只能裸套 GA / PSO；
- 无法形成结果证据；

那就不应该仅凭兴趣硬选。

### 推荐的个人默认打法

\[
\boxed{
\text{Exact Formulation}
\rightarrow
\text{Problem-specific Representation}
\rightarrow
\text{Heuristic / Search}
\rightarrow
\text{Local / LP / CP Refinement}
\rightarrow
\text{Independent Verification}
\rightarrow
\text{Bound / Gap / Certificate}
}
\]

如果规模允许，则优先尝试：

\[
\text{LP / MILP / CP-SAT / DP}
\]

如果规模过大，再转：

\[
\text{SA / GA / LNS / MCTS / Local Search / Hybrid}
\]

但元启发式必须围绕问题结构定制，而不是“看到优化题就遗传算法”。

- [ ] 每个 headline result 有 provenance
- [ ] 重要信息正文显式写，不让评委 infer

- [ ] 每个正式模型先写 Implementation Spec

# 十一、两次比赛最终总结

## 五一教会了什么？

> **不要把论文写成“我会多少模型”的展示。**

真正重要的是：

- 为什么选这个模型
- 为什么不用别的
- 指标是否真的有意义
- 物理机制是否进入结构
- 不确定性是否量化
- 评价协议是否提前定义
- validation 是否预留时间

五一最大的教训：

> **少堆模型，先定主线；指标要懂，物理要进结构；留预算做验证。**

---

## 华数杯教会了什么？

> **技术做出来以后，还要让评委一眼知道你做对了。**

真正重要的是：

- claim 不要过度收缩
- fancy branch 要狠删
- 沉没成本不能决定正文内容
- 统一 solver / 参数 / budget 要显式说明
- headline result 要有 provenance
- README 与代码不能替代正文信息架构
- narrative 不靠 method name 数量，而靠问题结构

华数杯最大的教训：

> **结果要硬，叙事要准，信息要前置。**

---

# 十二、最终一句话

以后比赛的默认哲学：

\[
\boxed{
\text{先数学模型}
\rightarrow
\text{冻结主线与评价协议}
\rightarrow
\text{设计 Solver / Verifier}
\rightarrow
\text{工程实现}
\rightarrow
\text{调参/消融/验证同步进行}
\rightarrow
\text{图片与证据同步产出}
\rightarrow
\text{只保留 survive 的方法}
\rightarrow
\text{Bound / Certificate 尽量闭环}
\rightarrow
\text{强证据支撑强结论}
}
\]

最后再压缩成八个字：

> **做少、做深、证据先行。**

对于算法优化题，再加八个字：

> **先证正确，再追最优。**

再加一条实验纪律：

> **主线求稳、支线求上限；模型先写 Spec，模块先写证据合同；调参找稳定区，消融判生死；结果出来前冻结，headline 必找第二条证据；轨迹全留，泄漏必查。**

以及一个更适合比赛现场贴在屏幕边上的版本：

> **先想清楚，再写代码；先留证据，再跑大算力；先拿小实例对拍，再拿大实例冲榜；失败分支别舍不得删；评委不负责替你考古。**
